# m6e-torrent confinement (P8.1, spec 8.4 and 8.5)

Two layers. The code layer is the primary one and always on; the sandbox is a second wall that needs the download folders to be known when the helper starts.

## Layer 1: path confinement in code (`src/confine.{hpp,cpp}`, `src/safety.{hpp,cpp}`)
- `checkInfoDict` (no file system) rejects traversal, absolute, empty, NUL, `:`, `\`, control-character, over-long (255 bytes a name, 1000 a path, 64 levels) and non-UTF-8 names, BEP 47 symlinks, padding entries without a `.pad/<digits>` name, and paths that collide by case or Unicode normalisation (NFD plus case fold, so `é` and `e` + accent, `Readme` and `README`). It checks the plain and the `.utf-8` name variants.
- `checkLayout` / `checkRelativePaths` (before payload transfer starts) resolve the save folder with `realpath` (it must exist, be a folder and not be `/`), then walk what already exists below it with `lstat`, never following a link: a symlink at any level, a file where a folder is needed, a folder or special file where a file is needed, a file with other hard links, and an existing name that differs only by case or normalisation (it would alias that file on APFS) are all `unsafe-path`.
- `prepareDirectories` and `openConfined` do the writes with `openat` and `O_NOFOLLOW` one component at a time from a descriptor of the root, so a link planted after the check still fails (`unsafe-path`). A hostile torrent cannot create a link (BEP 47 is rejected), so the remaining threat is a link that already exists in the chosen folder.
- `ensureProfileTorrentsDir` creates `<profile>/torrents` (0700) and rejects a link there.
- libtorrent opens the payload files itself, with plain `open`. The helper must therefore call `checkLayout` (or `checkRelativePaths` with the engine's own `file_path` strings, `pad` flags included) and `prepareDirectories` before `confirm` starts the transfer. Between that check and libtorrent's `open` only a local attacker with write access to the save folder could plant a link; the sandbox covers that case for everything outside the allowed folders.
- Link against `CoreFoundation` (already in the libtorrent link line). `foldName` uses `CFStringNormalize` and `CFStringFold`.

## Finished files: execute bits and quarantine
`finalizeRelative(rootReal, "name/dir/file")` opens the file no-follow, checks it is a regular file, clears all execute bits (`fchmod`), and sets `com.apple.quarantine`:
1. First the mechanism Gecko uses for downloads (`CFURLSetResourcePropertyForKey` with `kCFURLQuarantinePropertiesKey`, type `LSQuarantineTypeOtherDownload`, see `CocoaFileUtils.mm`). On macOS 26 it writes `0281;<hex seconds>;;<UUID>`. It works inside the sandbox profile below.
2. If that leaves no attribute (checked with `fgetxattr` on the same descriptor), it writes `0081;<hex seconds>;M6E;<UUID>` directly with `fsetxattr`. `0081` is the flags value other browsers write for a download; this form (`flags;time;agent;UUID`) was not run through Gatekeeper here, only through the format test.
3. If both fail (a volume without extended attributes, such as FAT or some network shares), the call does not fail the download: `FinalizeReport.warning` says what was not done, and the helper should put it in the `completed` event or the log so the panel can show "could not quarantine".

## Layer 2: macOS sandbox (`m6e-torrent.sb`)
Deny-default SBPL. Allowed: IP sockets in and out on any address and port (`(remote ip)`, `(local ip)`) and, of the `AF_UNIX` sockets, only the DNS resolver's `/private/var/run/mDNSResponder` (no ssh-agent, gpg-agent or Docker socket); `system-socket` only for route sockets and kernel controls (as Gecko's socket process); `sysctl-read` of `hw.*`, `machdep.cpu.*`, `net.*` (routes and interfaces), `sysctl.*`, the helper's own `kern.proc.pid.*` and a few system version names, not the process list or `kern.procargs2`; process information only about itself (`process-info*`, which `(deny default)` does not cover, is denied); `file-read-metadata` only of the folders on the way to the allowed ones (computed from the parameters by the profile's `ancestors` function, for `realpath` and `lstat`), the allowed folders and the system folders; read of the helper binary, `/usr/lib`, `/System/Library`, a few `/dev` and `/etc` files; read and write under `DOWNLOAD_1` to `DOWNLOAD_4` and `TORRENTS_DIR` (`<profile>/torrents`); `INBOX_DIR` read-only, even when it is inside `TORRENTS_DIR` (a later `deny file-write*` rule: in SBPL the last matching rule wins); `mach-lookup` of configd, the DNS configuration service, mDNSResponder and `com.apple.PowerManagement.control`. Process execution: none, except that under `sandbox-exec` the helper binary itself (`EXEC_HELPER=YES`). The `sysctl` list is what the helper read in every test run (found with an interposed `sysctl`), plus the version names the system libraries commonly read.

Parameters, all required, all `realpath`s (`/tmp` is `/private/tmp`): `HELPER`, `EXEC_HELPER`, `DOWNLOAD_1..4` (an unused slot repeats an allowed folder; the helper uses `TORRENTS_DIR`), `TORRENTS_DIR`, `INBOX_DIR`.

Two ways to apply it:
- `/usr/bin/sandbox-exec -f m6e-torrent.sb -D HELPER=... -D EXEC_HELPER=YES ... m6e-torrent ...`
- In the helper at start, which is what `--sandbox` does (`PROTOCOL.md`, "Additions (helper-sandbox, P8.1)"): `main` resolves `--profile-dir`, `--inbox-dir` and every `--download-dir`, then calls `m6e::enterSandboxWithProfile(kSandboxProfile, params, &error)` with `EXEC_HELPER=NO`, before the engine starts and before it reads standard input. After it, nothing can be executed at all, not even the helper binary again. `kSandboxProfile` (`src/sandbox_profile.hpp`) is a copy of this file compiled into the helper, so nothing has to be installed next to it or found at run time; `tests/sandbox` fails while the two differ.

The power rule is needed for the idle-sleep assertion (spec 8.4) and the configd rule for libtorrent's interface and gateway lookups; the test proves each: without its `mach-lookup` line `power` and `configd` fail. DNS for `localhost` and a public name worked without the mDNSResponder line on macOS 26; it stays in because older systems and SOCKS/VPN setups may need it.

### Proof (`tests/confine/run.sh`)
`tests/confine/sandbox_proof.sh` runs the real code (`sandbox_probe`) under both ways of applying the profile and checks, with 41 cases: it writes inside each download folder and the profile folder (including through `openConfined`, creating folders), reads the inbox, finalizes a file (execute bit gone, quarantine set), uses loopback TCP and UDP, lists interfaces, opens a route socket, resolves `localhost`, takes a power assertion and reads configd; and it is denied writing outside, through a link out of the folder, into the inbox, in `/tmp` and in `$HOME`; reading outside, listing `$HOME` and `/Users`, reading a file in `$HOME`, `/etc/passwd`, the Keychains folder; `exec`, `posix_spawn` of `/bin/echo` and `/bin/sh`; and `fork`.

### Proof with the real helper (`tests/sandbox/run.sh`)
The proof above runs a probe. `tests/sandbox/run.sh` runs the real `m6e-torrent` under `--sandbox`:
- `sandbox_tests.py` checks the command line, then asks the kernel (`sandbox_check` through `sandbox_query.c`) what the live helper may do: exec of `/bin/sh`, `/bin/echo` and the helper itself, and fork, are denied; writing is allowed in both download folders and the profile, denied in the inbox, outside, in `$HOME` and in the parent folder; reading is allowed in the inbox, denied outside, in `$HOME`, `/etc/passwd` and the Keychains folder. Then it uses the sandboxed helper for real: a loopback download whose tracker is named `localhost` (DNS) holds the power assertion (`pmset -g assertions`), is quarantined and has its execute bits cleared. It also checks that `confirm` refuses a folder outside, that `add` cannot read a `.torrent` outside, and that a saved torrent in a folder that is no longer allowed stays paused with `unsafe-path`.
- **A link planted after the check.** After `confirm` has checked the folder, the test replaces the torrent's folder (or, for a single file, the file) with a symbolic link to a folder outside. Unsandboxed, libtorrent follows it and writes outside (the control test shows this). Under `--sandbox` the write fails with "Operation not permitted", the torrent goes to `error`, and nothing outside changes. This is the case the code layer cannot close (gap 6) and the sandbox does.
- Then `run_tests.py` (27 tests) and, with `--privacy`, `privacy_tests.py` (29 tests: SOCKS5, IPv6, uTP, web seeds, kill switch, IP filter, seeding goals and the rest) run unchanged against the helper under `--sandbox` through `tests/sandbox/m6e-torrent-sandboxed`. For the conformance tests the launcher allows `<test>/save` and the disk-full volume `<test>/small`, with `<test>/in` as the inbox. The privacy tests create their save folders after the helper starts, so there the whole test folder is the download folder; as the helper refuses a download folder that contains its profile, the launcher moves each profile to `<test>.profiles/<helper>` and leaves a link in its place.
- `tests/security/run.sh` (security review fixes, P8.5) runs `net_probe` under this file with the same parameters: a connection to an `AF_UNIX` socket of the test is refused, the mDNSResponder socket, loopback TCP and UDP work; `kern.proc.all` and another process's `kern.procargs2` are refused, `hw.ncpu` and `kern.osversion` work; `stat` of `~/Library` is refused. It also asks the live helper under `--sandbox` the same through `sandbox_check`.

Nothing the helper needs was blocked on macOS 26 (Darwin 25.6, arm64): no missing `mach-lookup`, `sysctl` or file rule showed up in any of these runs, and the profile needed no new allow rule (only the inbox `deny`). The quarantine attribute is written by the LaunchServices route (`0281;…`) even though `com.apple.coreservices.launchservicesd` is denied.

### Gaps (open, for the lead)
1. **Download folders are fixed at start.** Decided (CONTRACTS.md, "Additions (service, P8.1)"): the service passes up to four folders (the default download folder, then the ones confirmed before) and restarts the helper when the user picks another one. A saved torrent whose folder has left that list is loaded paused at `restore` with `unsafe-path`, and resuming it fails until the folder is allowed again. A remembered folder that no longer exists makes the helper exit with status 2, so the service must drop such folders before starting it.
2. **Input files.** Done: the service stages a `.torrent` and an IP-filter file into `<profile>/torrents/inbox/`, which is the helper's default inbox. Under `--sandbox` `add` can read only the inbox, the download folders and the profile.
3. **`file-read-metadata`** is limited to the folders on the way to the allowed ones and the system folders (P8.5). A path elsewhere still answers "no such file" rather than "not permitted" when it does not exist, so a compromised helper can tell whether a path exists, not its size, times or content.
4. **IP network is not narrowed**: the helper may reach any IP host and port (but no `AF_UNIX` socket other than mDNSResponder's). Interface binding and the proxy are the helper's job (8.5).
5. **Deprecation.** `sandbox-exec` and `sandbox_init_with_parameters` are deprecated by Apple but ship in every macOS from 11 to 26 and are what Chromium and Gecko use. Tested only on macOS 26 (Darwin 25.6) on arm64; not on macOS 11.
6. **Hard links**: an existing file with other hard links is refused, but a link made by the user between the check and the open is not caught (local attacker case).
7. **Debug output**: macOS gives no sandbox denial log to a normal user here (`log show` is denied), so a rule that is missing on another macOS shows up as the helper aborting at start (exit 134) or `Operation not permitted`. Run the proof script on each target macOS.
